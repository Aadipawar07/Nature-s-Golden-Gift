PART 1 - Executive summary
1.1 Verdict
LAUNCH READINESS: NOT READY.  The repository is a well-organised scaffold with a partly built storefront UI. There is no backend logic, no authentication, no payment, no inventory, no shipping and no admin. Nothing in the repo can take an order, move money or ship a parcel. Do not send paid traffic to it.
The PDF describes a premium, secure D2C turmeric store with a CRM. The repo has delivered roughly the PDF's Phase 0 (structure only) and about a third of Phase 1 (static storefront). The good news: the scaffold is clean, nothing is mis-built that would need to be torn out except the items in section 2.4, and every difficult decision (state machines, idempotency, atomic stock, webhooks) is already specified in the PDF and just needs to be built in the right order.

1.3 Recommended architecture (summary)
Keep the PDF baseline: modular-monolith Express API, MongoDB Atlas/Mongoose, React + Vite storefront and a separate React + Vite CRM, Firebase Auth, Razorpay, Shiprocket, Cloudinary, Vercel (x2), GitHub Actions (ADR-001).
Restructure the repo now, while it is cheap: frontend/ becomes apps/storefront/, backend/ becomes server/, add apps/crm/ and packages/shared/ as npm workspaces (ADR-002). All backend files are stubs, so this costs about half a day.
Replace JWT with Firebase Auth in the repo and in docs/architecture.md (ADR-003).
API host: recommend Render (always-on paid instance, Singapore region) over Railway, subject to owner approval and a pricing check (ADR-004).
No Cloudflare Workers/D1, no AI provider in MVP (ADR-006, ADR-007).

1.5 Top risks and decisions
RISK-001 Timeline vs. business goal. Remaining build is 3-10 months depending on weekly hours. A first-month revenue goal cannot be met through this platform. Decide an interim sales channel (OI-017) rather than rushing the money paths.
RISK-003 Claims and compliance. The UI shows "Certified 100% Organic", an FSSAI badge without a licence number, sample testimonials, and therapeutic benefit wording, all of which the PDF forbids until evidenced (F-008).
D-003 Two design directions. The repo follows the earlier bracket/blueprint look; the PDF defines a different token system. Pick one before building primitives (OI-019).
RISK-004 Razorpay activation requires KYC and four live legal pages (PDF Doc 10.5). Start KYC early; it runs in parallel with development.

See Part 21 for the full register. The five that block the most work: sourcing facts and certifications (OI-001/002), final SKUs, prices and weights (OI-004/005), design direction (OI-019), shipment-creation trigger (OI-014), and the interim sales plan (OI-017).

4.2 Why a modular monolith (ADR-001)
Volume: tens of orders per day (PDF Doc 07). The risk is an unmaintainable system, not an unscalable one.
Transactions: payment confirmation + stock deduction + order status must commit together. One process and one database make this a plain Mongo transaction instead of a distributed saga.
One developer: NFR-07 requires one person to hold the backend in their head.
Escape hatch: layering (route -> middleware -> controller -> service -> model, integrations behind adapters) lets a module be extracted later without a rewrite.
4.3 Request lifecycle and layering (A, Doc 07)
request -> requestId + pino log -> helmet/CORS -> rate limit -> [rawBody if /webhooks]
        -> auth (Firebase verifyIdToken -> users lookup) -> requireRole / requireOwnership
        -> validate (Zod body/params/query) -> idempotency (mutating payment/shipment/refund)
        -> controller (parse, shape response only) -> service (rules + transactions)
        -> integration adapter (razorpay / shiprocket) | model (Mongoose)
        -> errorHandler (AppError -> { success:false, error:{code,message} }, no internals leaked)

PART 12 - Payment and order correctness
12.1 Non-negotiable rules (all designed and tested)
The backend, not the browser, computes authoritative totals from current DB prices, quantities, coupon rules and shipping. Money is integer paise; no floating-point arithmetic.
Razorpay secrets are backend-only. Signatures are verified server-side with crypto.timingSafeEqual. Webhook routes use the raw body.
Webhook events are persisted before processing, deduplicated by {provider, eventId}, and processed idempotently; browser closure after payment must not lose the order.
Stock is deducted atomically, exactly once, only after verified payment. Order, Payment, Shipment and Return are separate state machines.
A paid order is never cancelled or reversed because Shiprocket is unavailable. Refunds are validated against captured amount, support partial amounts, and are finalised by webhook/reconciliation.
Customer ownership is checked server-side on every customer resource; admin roles are enforced server-side; every sensitive admin mutation is audited.

S-07
Two customers buy the last unit concurrently
State: one deduction matches, the other gets modifiedCount 0. If money was already captured for the loser: order CONFIRMED with stockDeducted:false + REQUIRES_ATTENTION; admin restocks or refunds. Never silently void a paid order. Test: TEST-021, 024.
S-08
Shiprocket unavailable after payment capture
State: order CONFIRMED, payment PAID, shipment missing/FAILED. Retries: 1 m, 5 m, 15 m, 1 h x3 then SHIPMENT_CREATION_FAILED alert. Customer: "Order confirmed; dispatch delayed" - no cancellation. Admin: retry button; no automatic refund or cancel. Test: TEST-035.
S-09
Shiprocket token expires mid-request
State: 401 -> force refresh, retry once; second failure alerts. No duplicate order: reconcile by order_id. Test: TEST-038.
S-10
Shipment webhook arrives late or regresses status
State: appended to trackingEvents[]; status unchanged unless newer rank or whitelisted regression. DELIVERED shipment advances order to DELIVERED.
S-11
Refund request retried, or refund webhook delayed
State: Idempotency-Key + Razorpay receipt dedupe the retry; refund stays pending until refund.processed/refund.failed. Sum of refunds validated before every call. Admin: sees pending refund in work queue.
S-12
Admin repeats an action after a timeout
State: idempotency key returns the cached 24 h response; guarded transitions make a second cancel/refund a no-op or 409.
S-13
Deploy or DB rollback during active orders
State: additive-only migrations; backward-compatible API; webhooks persisted before processing so events received during rollback are replayable from /admin/webhooks. Recovery: reconcile job re-fetches payments from Razorpay for orders PENDING_PAYMENT in the window.

12.4 Reconciliation
reconcilePayments job (scheduled; also admin-triggered per payment): for PENDING_PAYMENT orders older than a few minutes and for payments in CREATED, fetch the payment from Razorpay and run the same idempotent confirmation service. This is the backstop for lost webhooks. A daily report compares Razorpay captures with local PAID payments and flags differences to the dashboard.

PART 13 - Inventory correctness
Atomic deduction: the database filter { "variants.stock": { $gte: qty } } is the guard; there is no read-then-write. Implementation card: MOD-09.
Transaction boundary: payment status, all stock lines and order status commit together or not at all.
Idempotency: orders.stockDeducted flag, set in the same transaction; restore sets it back; each is a no-op the second time.
Movement table (A, Doc 15.3): verified payment -qty; pre-shipment cancel +qty; RTO delivered +qty (admin-confirmed); return QC pass +qty; QC fail none (DISCARD); manual adjustment +/- with mandatory reason and audit.
Display: OUT_OF_STOCK (disabled, visible); LOW_STOCK with "Only N left" (genuine, never fabricated); IN_STOCK hides exact count. Alerts fire once per crossing.
Oversell proof: TEST-021 against a real replica set (not a mock) - 20 parallel attempts, stock 10 -> exactly 10 succeed, final stock 0.
Deferred (V2): 15-minute reservation. Revisit when a variant sells over 20 units/day or flash sales start.

14.2 NDR, RTO, retries and outage
NDR: shipment stays IN_TRANSIT; ndrDetails recorded; customer notified to reschedule; admin NDR queue. After 3 failed attempts the courier initiates RTO.
RTO: RTO_INITIATED notifies both; on RTO_DELIVERED restock, then refund per the owner's RTO policy (admin-initiated, never automatic).
Outage: exponential backoff (1 m, 5 m, 15 m, 1 h x3), then alert; the paid order is never cancelled or refunded automatically.
No courier serviceable: shipment held at CREATED; admin picks a courier manually.
Idempotency: a duplicate order_id rejection is treated as success - fetch the existing Shiprocket order and reconcile locally.

PART 16 - 3D, animation and performance
Principle (A): a beautiful static fallback beats a broken or slow 3D experience; 3D is the designated schedule buffer.
Strategy: React Three Fiber scene loaded lazily after first paint; never on the critical render path; mobile, low-end and reduced-motion get a pre-rendered poster with 2-layer CSS parallax (no WebGL). Manual motion toggle. FPS monitor degrades to the poster.
GSAP: scroll reveals and a pinned journey on desktop only; mobile gets a vertical five-card stepper.
Budgets (A): 3D adds <= 400 KB gzip; LCP <= 2.5 s on mid-tier Android over 4G; INP <= 200 ms; CLS <= 0.1; Lighthouse mobile >= 85 on key commerce pages.
Baseline (B): the storefront main bundle is 91 kB gzip today (no animation or Firebase libraries yet). Add size-limit in PH-00 so growth is visible.
Measurability: budgets must be measured on a real mid-tier Android over throttled 4G, not only in desktop Lighthouse (TEST-052). Lab scores alone do not prove the INP target.

Do not run PH-05 to PH-08 in parallel: each depends on the previous being correct and each is individually subtle.
Start owner-side tasks (KYC, legal text, SKU data, photos) in week 1 so they never block the critical path.
Hold a review gate at the end of each phase: acceptance criteria met, tests green, evidence recorded, docs updated, then and only then start the next.
Protect PH-04 to PH-06 from interruption; these carry the highest defect cost.
